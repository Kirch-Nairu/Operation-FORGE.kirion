## System purpose

KIRION Forge is a portable engineering operating system for coordinating capable AI agents through durable project memory, explicit authority, bounded roles, disposable sandboxes, structured handoffs, evidence-based validation, controlled integration, deliberate promotion, and recoverable execution.

## Accepted operating thesis

Forge uses **Decision Surface Compression**: move repeatable, high-branching project reasoning into durable and reviewable structures before implementation reaches a Code Writer while preserving local engineering judgment for contradictions, defects, unsafe actions, stale assumptions, and implementation decisions.

## Accepted architecture

Forge contains accepted operational layers for:

- an obvious human-facing `00_START_HERE/` root entrypoint with thin copy-paste launchers for Maintainer, Code Writer, and Integration Writer sessions;
- bootstrap and capability/authority handshake;
- repository/agent constitution;
- doctrine and role contracts;
- state-transition protocols;
- memory lifecycle, reconciliation, compaction, supersession, and continuity;
- exact Git authority, branch semantics, promotion, rollback, and recovery;
- risk-selected validation, failure taxonomy, CI interpretation, and evidence manifests;
- recoverable Sandbox Capsules;
- instruction-trust, external-content, destructive-action, and secret boundaries;
- parallel writer ownership/dependency/collision coordination;
- candidate/project/nest state models;
- checklists and templates;
- JSON structural contracts;
- read-only Forge conformance/authority helpers;
- GitHub Actions structural validation;
- behavioral evaluation scenarios and structured result recording;
- source-anchored case studies from Talibon, Tapost, and SentinelOps, with hardened integration notes that preserve historical facts and claim limitations;
- repository-local Forge nest.

## Accepted role model

Primary roles:

- Maintainer
- Code Writer
- Integration Writer
- Reviewer
- Acceptance Agent

Implementation does not equal acceptance. Writers produce bounded candidates and do not automatically integrate or promote their own work.

## Accepted project-entry model

For normal human use, begin at `00_START_HERE/` and paste the appropriate thin launcher into a fresh agent conversation. The launcher points back to canonical Forge files and does not replace them.

### New projects

Role Call → Discovery/Digestion → Architecture → Repository/Nest → Handoff.

### Existing projects

Role Call → Read-only Reconnaissance → Report → explicit Nest Authorization → Baseline Capture → Nesting → Nest Completion → fresh Code Writer Bootstrap Packet.

## Memory model

Forge separates model knowledge, user memory, Forge doctrine, project durable memory, and transient session state. Hot/warm/cold retrieval, compaction, supersession, and reconciliation are accepted. Observable Git/runtime state outranks stale memory.

## Evidence model

E0 through E7 remain the shorthand evidence ladder. Evidence manifests additionally record claim, type, provenance, candidate SHA, environment, command/scenario, result, artifact reference, observation time, and limitations.

Real case studies must preserve source facts, Forge interpretation, lessons, and limitations as separate concepts. Stronger evidence for one claim does not automatically transfer to neighboring claims.

## Git / promotion model

Routine substantial Forge development uses explicit candidate branches and Maintainer-governed acceptance/promotion. Promotion fails closed on authority drift and requires post-promotion verification plus durable-memory update. Force pushes remain prohibited by default.

Independent candidates may be integrated through a provenance-preserving Integration Writer wave before Maintainer acceptance.
